1. Requirements and system design
This section is about deciding what you're building and how the pieces will work before you start implementing them.
1.1 Gather and finalize functional requirements
Functional requirements describe what the system must do.

For your ERP, examples include:
- A student can view their profile, register for courses, view grades, check attendance, and view fee records.
- A faculty member can view assigned courses, record attendance, and enter marks for those courses.
- Finance staff can manage fee records.
- An administrator can manage academic data and view administrative reports.
- An authenticated user can ask the AI helpdesk questions that they are authorized to ask.
What you actually do: Write down the required features for every user role. Turn vague requirements into specific actions, and agree on what counts as completed functionality.

Deliverable: A requirements document or checklist that the whole team follows.
1.2 Define non-functional requirements
These describe how well the system should work, rather than which features it has.

Examples:
- Security: students cannot view another student's private records.
- Performance: ordinary pages and database queries should respond within an agreed time.
- Reliability: errors should not leave registrations or grades in an inconsistent state.
- Usability: users should be able to navigate the system without unnecessary complexity.
- Maintainability: the code should be organized into understandable modules.
- AI reliability: the helpdesk should use evidence and admit when it cannot answer.
What you actually do: Define measurable acceptance criteria where possible. For example, decide what response-time target to test, rather than simply writing “the system should be fast.”

Deliverable: A short list of quality, security, and performance requirements.
1.3 Finalize project scope and features
This is where you decide what is included in your final-year project and what is not.

Your current scope includes profiles, courses, registration, grades and GPA/CGPA, attendance, fees, announcements, dashboards, reports, a document-based RAG helpdesk, and authorized ERP-connected AI queries.

CLO/PLO attainment and a separate notification subsystem are excluded.

What you actually do: Confirm the included modules, define the minimum working version of each, and prevent extra features from quietly expanding the project.

Deliverable: A finalized scope document. A real payment gateway and a full production rollout across an entire university are not necessary unless your supervisor explicitly adds them.
1.4 Define user roles and permissions
Decide who can see and change each kind of information.
Role	Typical permissions
Student	View own profile, registration, grades, attendance, and fee records
Faculty	View assigned courses and authorized student records; enter marks and attendance for assigned courses
Finance staff	Manage authorized fee records and payment statuses
Administrator	Manage authorized users and academic configuration, and view administrative reports

What you actually do: Create a permission matrix. For example, determine whether faculty can edit marks after submission, who can change a student's registration, and whether administrators can access finance records.

Deliverable: A role-and-permission table that guides both the backend and frontend.
1.5 Identify end-to-end university workflows and use cases
A workflow describes the sequence of steps required to complete an operation.

For example, course registration might work like this:
1. A student logs in.
2. The student opens the course offerings for the current semester.
3. The student selects a course.
4. The backend checks prerequisites, available seats, and duplicate registration.
5. The backend saves the registration if it is valid.
6. The interface displays success or explains why the registration failed.
What you actually do: Document similar workflows for adding courses, entering marks, calculating GPA, recording attendance, and viewing fees. Also include failure cases.

Deliverable: Use-case descriptions and workflow diagrams.
1.6 Review existing ERP and university AI helpdesk systems
This means examining existing products to understand which features they offer and what your project needs to demonstrate.

You can compare your selected systems by their academic modules, registration, grading, finance, reporting, AI capabilities, permissions, and limitations.

What you actually do: Use your existing product comparison matrix, verify the features using available product documentation, and identify the specific gap your project addresses.

Deliverable: A comparison matrix and a concise explanation of your project's purpose. You do not need to rebuild this research if your matrix is already complete.
1.7 Design the overall system architecture
Decide which components exist and how they communicate.

For example:
- React displays pages and sends requests.
- FastAPI validates requests and applies business rules.
- PostgreSQL stores university records.
- The RAG pipeline searches approved documents.
- LangGraph coordinates specialist agents.
- AI agents call permitted backend tools when they need ERP information.
What you actually do: Draw a component diagram and define the responsibilities of each component.

Deliverable: A system architecture diagram.
1.8 Design the database ERD and relational schema
An ERD is a diagram showing the entities in your database and the relationships between them.

Possible entities include:
- User, Student, Faculty
- Department, Program
- Course, Semester, CourseOffering
- Registration, Assessment, Grade
- AttendanceRecord
- FeeRecord
- Announcement
- Document and document-chunk metadata
What you actually do: Decide which tables are required, what information each table stores, and how they relate. For instance, a student can have many registrations, while a course offering belongs to a particular semester and course.

Deliverable: An ERD and a table/schema design.
1.9 Define database relationships, constraints, and normalization
This is about making sure your database stores information consistently.

Examples:
- Each user has a unique login identifier.
- A registration refers to an existing student and course offering.
- The same student cannot register for the same offering twice.
- A grade cannot refer to a nonexistent registration.
- Student information should not be duplicated in every course registration row.
What you actually do: Define primary keys, foreign keys, uniqueness rules, appropriate data types, and validation constraints. Normalize tables to reduce duplicated data and update anomalies.

Deliverable: A consistent relational schema with documented constraints.
1.10 Define backend API structure and module boundaries
An API is how the frontend or another component requests functionality from the backend.

Examples of endpoints could be:
- GET /courses — retrieve available courses.
- POST /registrations — request course registration.
- GET /students/me/grades — retrieve the authenticated student's grades.
- GET /fees/me — retrieve the authenticated student's fee records.
These are illustrative endpoint names; your team will finalize the actual API design.

What you actually do: Decide which endpoints exist, what data they accept and return, who can use them, and which backend module owns each operation.

Deliverable: An API specification, including request/response examples and permission requirements.
1.11 Design the multi-agent architecture and communication workflow
Decide which agents exist, what each is responsible for, and when the system invokes them.

Your proposed agents are:
- Policy and Information Agent: answers questions from approved university documents.
- Academic Records and Registration Agent: handles authorized academic-record queries.
- Finance and Student Services Agent: handles authorized fee and relevant administrative queries.
- Shared orchestrator: decides where questions should go and combines results.
What you actually do: Draw the workflow from receiving a query to routing it, calling the necessary tools, checking results, and returning an answer.

Deliverable: An agent architecture diagram and a clear responsibility definition for each agent.
1.12 Define security boundaries between the AI system and ERP backend
The AI model should not become an unrestricted route into the university database.

What you actually do: Define which tools agents can call, which data each tool can return, how the authenticated user's identity and role are passed through, and where permissions are checked. Decide what happens when a user asks for somebody else's information.

Deliverable: A security design documenting how the backend protects data even if an AI agent makes an incorrect request.

2. Database and backend foundation
This is the base on which all the ERP modules depend. If it is poorly designed, every subsequent module becomes harder to implement.
2.1 Set up the PostgreSQL database
Install or configure PostgreSQL, create the project database, and establish the connection settings the backend will use.

What you actually do: Configure the database name, credentials, connection string, and development environment. Confirm that the backend can connect successfully.

Deliverable: A running database accessible from your FastAPI application.
2.2 Create database models and relationships
Database models define how tables are represented in your Python code, commonly using SQLAlchemy.

For example, a Student model might contain a student identifier, linked user account, program, and other approved profile fields. A Registration model would link a student to a course offering.

What you actually do: Create the SQLAlchemy models, define their fields and relationships, and ensure they match your ERD.

Deliverable: Working Python models corresponding to your database design.
2.3 Implement database migrations
Migrations are controlled changes to the database structure over time.

For example, if you later add a field to a course offering, a migration applies that schema change without manually rebuilding the whole database.

What you actually do: Set up Alembic, generate and review migrations, and verify that a new database can be created from the migration history.

Deliverable: Version-controlled database changes that team members can reproduce.
2.4 Add keys, constraints, and validation constraints
This is the implementation of the rules defined in the schema.

What you actually do: Add primary and foreign keys, unique constraints, required fields, appropriate checks, and request-level validation. Database constraints should protect data even if a request bypasses a frontend validation rule.

Deliverable: A database that rejects invalid relationships and duplicate records where prohibited.
2.5 Create seed data and synthetic test accounts
Seed data is sample information used to develop and demonstrate the application.

You might create fictional students, faculty members, courses, semester offerings, registrations, attendance records, and fee records.

What you actually do: Write scripts that populate the database with consistent, clearly fictional records. Create demonstration accounts for the required roles.

Deliverable: A repeatable way to set up a usable demo environment without exposing real student data.
2.6 Set up the FastAPI backend
FastAPI is the Python framework that will receive requests and expose your application APIs.

What you actually do: Create the project structure, configure the application, connect the database, organize route handlers and services, and provide basic health-check and API documentation endpoints.

Deliverable: A functioning backend that can receive requests and interact with PostgreSQL.
2.7 Implement common request validation and error handling
Requests may contain missing fields, invalid IDs, incorrect formats, or values that violate business rules.

What you actually do: Define Pydantic request/response schemas, validate inputs, return consistent error messages, and prevent unexpected exceptions from exposing sensitive information.

For example, attempting to register for a full course should return a meaningful error rather than a generic server crash.

Deliverable: Predictable input validation and error responses across the application.
2.8 Establish REST API conventions
Consistency makes the APIs easier to develop, test, and maintain.

What you actually do: Agree on endpoint naming, HTTP methods, response formats, pagination where needed, status codes, and error structures.

Deliverable: A consistent API style used by every backend module.
2.9 Implement authentication and secure password hashing
Authentication establishes who is logging in.

What you actually do: Implement login, password verification, session or token handling, logout or token invalidation as appropriate, and secure password hashing. Never store plaintext passwords.

Deliverable: Users can authenticate and receive an identity the backend can verify on subsequent requests.
2.10 Implement role-based access control (RBAC)
RBAC determines which actions a user is allowed to perform based on their role and permissions.

What you actually do: Implement permission checks in backend dependencies or service functions. For example, faculty should not be able to edit marks for a course they do not teach merely because they have the faculty role.

Deliverable: Role-aware backend authorization.
2.11 Implement server-side authorization for protected records and operations
A role alone is not enough. The backend must also verify which specific record the user can access.

What you actually do: Check the authenticated user, record ownership, assigned courses, and applicable permissions on every protected operation. For example, a student should be able to retrieve their own grades without being able to change the student ID in the request and retrieve someone else's grades.

Deliverable: Record-level access controls that prevent unauthorized data exposure.
2.12 Implement common database transaction and integrity handling
A transaction ensures that related database changes succeed or fail together.

For example, if course registration involves creating a registration record and updating related state, the operation must not leave the database partially updated if an error occurs.

What you actually do: Use transactions, handle concurrent requests, and decide how the system behaves if two students attempt to take the final seat in a course at the same time.

Deliverable: Consistent data even when operations fail or requests overlap.

6.5 Calculate GPA
GPA summarizes performance across courses for a particular academic period, using the institution's grading rules and credit-hour weighting.

A common weighted formula is:
\[
\text{GPA} =
\frac{\sum_i(\text{grade points}_i \times \text{credit hours}_i)}
{\sum_i \text{credit hours}_i}
\]

What you actually do: Implement the calculation using the configured grade-point scale and applicable courses. Decide how retakes, withdrawals, incomplete grades, and failed courses are treated according to your project's rules.

Finished result: The system produces GPA values that can be checked against manually calculated examples.
6.6 Calculate CGPA
CGPA summarizes academic performance across the relevant completed semesters.

What you do: Aggregate the applicable grade points and credit hours across semesters, following the chosen institutional rules. Avoid simply averaging semester GPAs unless that is specifically the correct calculation for your rules.

Finished result: Students can view their cumulative academic performance.

Finished result: Automated tests demonstrate that the calculations follow the configured rules.

10. RAG document retrieval pipeline
This is one of the most important AI components of your FYP. RAG stands for Retrieval-Augmented Generation. It allows the AI to answer questions using relevant information retrieved from your university documents instead of relying only on what the model learned during training.

For example, if a student asks, “What is the procedure for withdrawing from a course?”, the system searches approved academic policies and uses the relevant passages to construct an answer.
10.1 Collect approved university documents or prepare synthetic documents
What you do: Gather documents that the system is allowed to use, such as academic regulations, course registration guidelines, grading policies, and fee policies. If real documents are unavailable, prepare clearly labelled synthetic documents for the prototype.

Finished result: A defined collection of documents against which the helpdesk can retrieve information.
10.2 Implement document ingestion
Ingestion is the process of importing documents into your system.

What you do: Create a process that accepts supported files, extracts their content, and stores the relevant metadata. Track information such as the document title, version, and ingestion status.

Finished result: Documents can be added to the RAG knowledge base through a repeatable process.
10.3 Extract text from supported document formats
Documents can contain text in different formats, such as PDF or DOCX.

What you do: Use appropriate parsing libraries to extract readable text. Handle empty files, unsupported formats, extraction errors, and documents with difficult layouts. Scanned PDFs may require OCR if you decide to support them.

Finished result: The system can obtain usable text from the document formats you choose to support.
10.4 Split documents into searchable chunks
A large document is usually divided into smaller passages called chunks.

What you do: Choose chunk sizes and overlap settings, then split the extracted text while preserving enough context. Associate each chunk with its original document and relevant page or section information where available.

Why it matters: If an entire 100-page policy is treated as one unit, retrieval may be too broad. Smaller chunks make it easier to find the passage that actually answers a question.

Finished result: Documents are represented as searchable passages with traceable source metadata.
10.5 Generate embeddings
An embedding is a numerical representation of text that helps a system compare semantic meaning.

For example, a question about “dropping a subject” might be semantically related to a document passage titled “course withdrawal,” even though the wording differs.

What you do: Select an embedding model, convert document chunks into vectors, and ensure queries are embedded in a compatible way. Your proposal mentions Sentence Transformers as one possible approach.

Finished result: Every indexed chunk has an embedding that can be used for semantic search.
10.6 Store embeddings in PostgreSQL using pgvector
What you do: Create a suitable database table containing the chunk text, document reference, metadata, and embedding vector. Configure pgvector and the relevant search index or query strategy.

Finished result: Your system can store and retrieve document embeddings within PostgreSQL.
10.7 Implement semantic retrieval
What you do: Convert a user's question into an embedding, compare it with stored document embeddings, and retrieve the most relevant passages.

You will need to choose retrieval settings, such as how many passages to return and whether to apply metadata filters.

Finished result: The RAG pipeline returns candidate passages related to a question.
10.8 Retrieve relevant document passages for a query
This task focuses on making retrieval useful for actual user questions, rather than just proving that vector search runs.

What you do: Test different question types, inspect retrieved passages, adjust chunking and retrieval parameters, and make sure irrelevant documents do not dominate the results.

Finished result: The system retrieves passages that are relevant enough to support an answer.
10.9 Select supporting evidence for AI-generated answers
Retrieval may return several passages, and not all of them will be useful.

What you do: Choose which passages provide evidence for the answer. Supply the selected evidence to the language model and instruct it to answer from that evidence rather than inventing unsupported policy details.

Finished result: The model receives relevant context before generating its response.
10.10 Preserve document references for source attribution
What you do: Keep each chunk's source document, title, and page or section information when available. Pass this metadata through retrieval and generation.

Finished result: The interface can show which approved document supports an answer.
10.11 Handle missing, irrelevant, or insufficient evidence
A reliable RAG system must sometimes say it cannot answer.

What you do: Establish rules for recognizing weak or insufficient retrieval results, avoid generating confident policy claims without evidence, and return a helpful fallback response.

For example: “I couldn't find a supporting policy in the available documents. Please consult the relevant university office.”

Finished result: The helpdesk can abstain rather than confidently inventing university rules.

11. Individual AI agents
Your multi-agent system should use a small number of specialist agents with distinct responsibilities. The agents are not separate copies of the entire ERP, and you do not need a separate agent for every ERP module.

An agent is a model-driven component that receives a task, follows instructions, and may call a limited set of tools to complete that task.
11.1 Policy and Information Agent
This agent handles questions answered by approved university documents.

What you do:
- Define the types of policy and general-information questions it handles.
- Give it access to the document retrieval tool.
- Provide instructions for using retrieved evidence.
- Require source references when supporting documents are available.
- Configure fallback behavior when evidence is missing.
Example: “What is the university's course withdrawal policy?”

The agent retrieves relevant policy passages and generates a grounded answer.

Finished result: A document-focused agent that can answer policy questions with supporting sources.
11.2 Academic Records and Registration Agent
This agent handles questions about academic information available through authorized ERP functions.

What you do:
- Define which academic queries it can handle.
- Connect it to permitted tools for courses, registrations, attendance, marks, grades, GPA/CGPA, and transcript-style records.
- Ensure calculations come from backend functions.
- Ensure protected data is retrieved only after server-side authorization.
Example: “Which courses am I registered for this semester?”

The agent requests the relevant records through an authorized backend tool and explains the result.

Finished result: An academic specialist that can answer supported queries using actual ERP records.
11.3 Finance and Student Services Agent
This agent handles fee information and other relevant administrative queries that fall within its defined scope.

What you do:
- Define which fee and administrative queries it can answer.
- Connect it to approved tools for fee records, balances, invoices, and payment statuses.
- Restrict access to financial records.
- Handle questions that fall outside its supported responsibilities.
Example: “What is my outstanding fee balance?”

The agent retrieves the balance through an authorized backend function.

Finished result: A finance-focused agent that reports actual recorded information instead of guessing amounts.
11.4 Define the responsibilities and tools available to each agent
What you do: Create a specification for every agent. Define its purpose, inputs, allowed tools, permitted outputs, and situations in which it should refuse or hand off a query.

For instance, the Policy Agent should not have unrestricted access to student financial records simply because it is part of the same AI system.

Finished result: Clearly separated responsibilities and minimal, purpose-specific tool access.
11.5 Implement each agent's instructions and request-handling logic
What you do: Write the prompts or instructions that guide each agent. Define how it interprets a request, uses available evidence, calls tools, handles missing data, and produces a response.

Finished result: Each specialist follows a consistent procedure rather than behaving as an unrestricted general-purpose chatbot.
11.6 Connect each agent to its required retrieval functions or backend APIs
What you do: Connect the Policy Agent to document search and connect the academic and finance agents to the appropriate backend tools. Define the input and output schemas for each tool.

Finished result: Agents can access the information they need through controlled interfaces.
11.7 Handle unsupported questions and agent errors
What you do: Decide what happens when an agent receives an unrelated question, a tool fails, a database request times out, or the requested record is unavailable. Return safe, understandable messages rather than fabricated answers.

Finished result: The agents fail gracefully and do not treat every tool error as if the requested information does not exist.

12. Multi-agent orchestration
The agents above are specialists. Orchestration is the logic that coordinates them. Your proposed framework is LangGraph.

Imagine LangGraph as a workflow that controls which agent runs, what state is passed between steps, and when the final response is returned.
12.1 Implement the shared LangGraph workflow
What you do: Define the graph's nodes, edges, state, and completion conditions. Nodes may represent routing, agent execution, tool calls, validation, and response generation.

Finished result: A functioning workflow that coordinates the specialist agents.
12.2 Implement query-intent classification and routing
The system needs to determine what kind of question a user is asking.

What you do: Classify requests into categories such as university policy, academic records, finance, or a combination of these. Implement routing rules that send each request to the appropriate agent.

Example: “How many credits am I taking, and what is the registration deadline?”

This may require the Academic Agent to retrieve the student's registration and the Policy Agent to retrieve the deadline.

Finished result: Queries reach the appropriate specialist instead of being handled by one generic chatbot.
12.3 Route questions to the appropriate specialist agent
What you do: Connect the intent classification result to the correct agent node. Define what happens when the intent is unclear or the request is outside the system's scope.

Finished result: The graph reliably selects the intended specialist.
12.4 Implement agent handoffs and tool invocation
Sometimes an agent needs another agent or a backend tool to complete a request.

What you do: Define how control passes between nodes, how tool arguments are validated, and how tool results return to the calling agent.

Finished result: Agents can perform permitted operations within a controlled workflow.
12.5 Handle queries requiring multiple steps or sources
What you do: Support workflows that require more than one retrieval or backend request. Define dependencies between steps and avoid unnecessary calls.

Example: To answer a question about whether a student satisfies a policy requirement, the system may need to retrieve the student's authorized academic information and the relevant policy passage.

Finished result: The system can answer supported multi-part questions using multiple sources.
12.6 Manage workflow state and error handling
What you do: Define which information is retained as the workflow progresses, how tool errors are represented, and when the graph should retry, stop, or return a fallback response.

Finished result: The workflow does not lose important information or continue indefinitely after a failure.
12.7 Combine agent results into a final response
What you do: Gather the relevant results from the agents, remove unnecessary duplication, and create a coherent final response. Preserve the source references for document-based claims.

Finished result: Users receive one understandable answer rather than disconnected outputs from several agents.
12.8 Implement fallback behavior when the system cannot answer reliably
What you do: Define conditions for stopping the workflow when the evidence is insufficient, a tool fails, or the request is unsupported. Avoid retry loops that repeatedly produce the same failure.

Finished result: The system can explain its limitations instead of pretending every query succeeded.
12.9 Display supporting sources when available
What you do: Pass source metadata from the retrieval pipeline through the graph to the frontend. Display document titles and page or section references where available.

Finished result: Users can inspect the documents supporting policy answers. ERP-record answers should be clearly distinguished from document citations; a database record is not the same kind of source as a university policy document.

13. Secure AI-to-ERP integration
This is where the AI helpdesk becomes genuinely connected to the ERP rather than just answering questions from documents.

It is also one of the most security-sensitive parts of the project.
13.1 Define the ERP backend tools that AI agents are allowed to use
A tool is a controlled function the agent can call.

Examples include:
- Search available course offerings.
- Retrieve the authenticated student's registrations.
- Retrieve the authenticated student's GPA/CGPA.
- Retrieve authorized attendance summaries.
- Retrieve the authenticated student's fee balance.
What you do: Specify each tool's purpose, required arguments, output format, permitted users, and error behavior.

Finished result: A limited, documented collection of backend functions available to the AI system.
13.2 Implement authorized read tools for student and academic records
What you do: Implement the academic tools using existing backend services or APIs. Derive the requesting user's identity from the authenticated context and check the relevant permissions.

Finished result: The AI can retrieve authorized academic records without being given unrestricted database access.
13.3 Implement authorized read tools for fee and finance records
What you do: Implement functions that retrieve permitted invoices, balances, and payment statuses. Check that the user is entitled to see the requested financial information.

Finished result: The finance agent can answer supported finance questions using actual records.
13.4 Pass authenticated user context into protected tool calls
What you do: Ensure tool calls are associated with the identity and permissions of the person who initiated the request. The model must not be trusted to declare its own identity or grant itself a role.

Finished result: A request made through the AI interface is subject to the same authorization rules as a request made through the ordinary ERP interface.
13.5 Enforce permissions on the backend for every protected tool call
What you do: Validate authorization inside the backend operation that retrieves or changes a protected record. Do not rely on an agent prompt saying “only access your own records.”

Finished result: The security rule is enforced even if the model generates an incorrect tool request.
13.6 Prevent agents from accessing unauthorized records
What you do: Limit tool access, validate record ownership and role permissions, and test adversarial queries such as requests to reveal another student's transcript or fee balance.

Finished result: Unauthorized data requests are rejected by the backend.
13.7 Ensure official calculations use backend business rules rather than AI-generated arithmetic
What you do: Have the agent call the official GPA, CGPA, fee-balance, or attendance-summary function instead of asking the model to calculate the value from conversational context.

Finished result: Official numerical answers come from deterministic code and database records, not potentially inaccurate language-model arithmetic.
13.8 Prevent unsupported AI answers from being presented as verified university facts
What you do: Separate retrieved evidence and tool results from generated explanations. Instruct agents not to invent policies, claim a registration succeeded without confirmation, or report a balance when the backend request failed.

Finished result: The interface communicates what the system actually verified.
13.9 Handle unauthorized requests and insufficient evidence safely
What you do: Define separate responses for access denied, record not found, service unavailable, and insufficient policy evidence. Avoid revealing sensitive details in error messages.

Finished result: The system handles security and information gaps without leaking private data.
13.10 Integrate the AI helpdesk into the ERP web interface
What you do: Add a chat interface, send authenticated requests to the backend, display the response and sources, and handle loading and error states. Ensure the backend associates the request with the current user.

Finished result: A user can ask questions through the same ERP application they use for academic and administrative tasks.
